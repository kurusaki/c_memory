## 1. スタックとヒープを寿命で比較する

一般的な実装では、スタックは関数呼び出しに伴う作業場所として使われ、普通のローカル変数や戻り先の情報などが関係します。ヒープは、mallocなどで実行中にメモリを動的に確保するために使われます。

ただし、C言語の規格がスタックやヒープという配置を必須にしているわけではありません。普通のローカル変数も、最適化によってレジスタで扱われたり、保存場所が不要になったりします。ここでは一般的な配置の説明と、C言語が保証する寿命のルールを分けて考えます。

| 比較する対象 | 普通のローカル変数（今回のint型） | mallocで確保した領域 |
|---|---|---|
| 一般的な配置 | スタック側 | ヒープ側 |
| 寿命 | 宣言を含むブロックの実行に伴い存在し、ブロックを抜けると終わる | 確保してから解放するまで存在する |
| 関数から戻った後 | その関数内の変数の寿命は終わる | 関数から戻るだけでは解放されない |
| 解放の管理 | 自分でfreeしない | 使い終わったらfreeする |
| 初期化 | 初期化を省略しても0になる保証はない | 確保直後の内容が0である保証はない |

ここでいう普通のローカル変数は、staticを付けていない自動変数です。関数内のstatic変数は静的記憶域期間を持ち、プログラムの実行中ずっと保存場所が存在するため、区別してください。

また、寿命が終わることと、保存されていたバイトがゼロに消去されることは別です。内容が残っているように見えても、寿命を終えた変数へアクセスしてはいけません。

## 2. サンプルプログラム

ファイル名：`stack_heap.c`

```c
#include <stdio.h>
#include <stdlib.h>

void show_local(void)
{
    int local_value = 100;

    printf("show_local: local_value = %d\n", local_value);
}

int *create_value(void)
{
    int *ptr = malloc(sizeof *ptr);

    if (ptr == NULL) {
        return NULL;
    }

    *ptr = 200;
    printf("create_value: *ptr = %d\n", *ptr);

    return ptr;
}

int main(void)
{
    show_local();
    puts("main: show_local returned");

    int *heap_ptr = create_value();

    if (heap_ptr == NULL) {
        fprintf(stderr, "Memory allocation failed.\n");
        return 1;
    }

    puts("main: create_value returned");
    printf("main: *heap_ptr = %d\n", *heap_ptr);

    free(heap_ptr);
    heap_ptr = NULL;

    puts("main: allocated memory freed");

    return 0;
}
```

### show_local：普通のローカル変数を使う

local_valueを100で初期化し、関数の中で表示します。show_localから戻ると、この変数の寿命は終わります。mainから指し先を使おうとする処理はありません。

### create_value：領域を確保してアドレスを返す

`malloc(sizeof *ptr)` でint型1つ分の領域を確保します。ここでの `sizeof *ptr` はint型のサイズを求める式であり、指し先の値を読み取る操作ではありません。

mallocが失敗するとヌルポインタを返すため、NULLかどうかを確認します。成功したら200を代入し、表示してからポインタ値を返します。mallocは確保した領域をゼロ初期化しないため、値を設定してから読み取っています。

### main：受け取った領域を使い、解放する

create_valueから返されたポインタ値をheap_ptrに受け取ります。NULLでないことを確認してから値を表示し、最後に `free(heap_ptr)` で領域を解放します。

確保に失敗した場合はエラーメッセージを標準エラー出力に表示し、終了コード1で終了します。成功時の出力とは異なります。

## 3. コンパイルと実行

リポジトリのルート（c_memory）から移動します。

```sh
cd samples/16_stack_heap
```

macOS・clangでコンパイルし、実行します。

```sh
clang -std=c17 -O0 -Wall -Wextra -Wpedantic stack_heap.c -o stack_heap
./stack_heap
```

`-O0` は英字のOと数字の0で、最適化を抑える指定です。この指定が具体的なメモリ配置を保証するわけではありません。

実行結果（2026年11月3日、macOS・Apple clang 21.0.0で実行確認。malloc成功時）：

```text
show_local: local_value = 100
main: show_local returned
create_value: *ptr = 200
main: create_value returned
main: *heap_ptr = 200
main: allocated memory freed
```

`main: show_local returned` の時点で、show_localのlocal_valueの寿命は終わっています。一方、`main: create_value returned` の後も、確保した領域から200を読み取れています。

この出力は、関数から戻った後も動的に確保したデータを利用できることを示します。スタックやヒープの境界、配置順を直接測定するサンプルではありません。

## 4. ポインタ変数自身と指し先を分ける

create_valueの実行中は、ローカルなポインタ変数ptrが、mallocで確保した領域を指しています。

```text
create_valueのローカル変数

ptr
┌──────────┐
│ アドレス │ ───────→ ┌─────┐
└──────────┘          │ 200 │
                      └─────┘
                    mallocで確保
```

`return ptr;` で呼び出し元へ渡すのはポインタの値です。ptr自身のアドレスを返しているわけではありません。

```text
create_valueのptr
→ 寿命が終了

mainのheap_ptr
┌──────────┐
│ アドレス │ ───────→ ┌─────┐
└──────────┘          │ 200 │
                      └─────┘
                    確保した領域は存続
```

mainのheap_ptrは、返された値を受け取って同じ領域を指します。ポインタ値をコピーしても、200を保存した領域がもう1つ作られるわけではありません。

heap_ptr自身もmainの普通のローカル変数です。「ヒープを指すポインタだから、ポインタ変数自身もヒープにある」とは限りません。

## 5. ローカル変数のアドレスを返す問題

説明用コード（問題のある例。サンプルへ追記せず、実行しないでください）：

```c
int *bad_create_value(void)
{
    int value = 200;

    return &value;  // 寿命が終わるローカル変数のアドレス
}
```

このvalueは、関数から戻ると寿命が終わります。返されたアドレスを使って呼び出し元からその指し先を読み書きすることはできません。寿命を終えたオブジェクトへのアクセスは未定義動作です。

たまたま200が表示されたり、異常終了しなかったりしても、正しい操作とは言えません。コンパイラが警告することもありますが、警告の有無だけで正しさを判断してはいけません。

今回のcreate_valueでは、関数から戻っても存在する動的に確保した領域を指す値を返しているため、これとは異なります。

## 6. 誰が解放するかを決める

今回の役割分担は次の通りです。

- create_value：確保し、初期値を設定して返す。
- main：値を利用し、使い終わったら解放する。

必要なfreeを呼ばず、確保した領域へのアクセス手段を失うと、メモリリークになります。また、解放した領域へのアクセスや、同じ領域の二重解放もしてはいけません。

ファイル名：`stack_heap.c`（抜粋）

```c
free(heap_ptr);
heap_ptr = NULL;
```

freeが解放するのは、mallocで確保した指し先の領域です。ローカルなポインタ変数heap_ptr自身を解放する操作ではありません。`free(&heap_ptr)` のように、普通のローカル変数のアドレスを渡してはいけません。

freeを呼んでもheap_ptrに自動的にNULLが代入されるわけではないため、今回は明示的に代入しています。この代入は、解放前のポインタ値を読み取らずに上書きします。

ただし、別のポインタが同じ領域を指していたとしても、その変数までNULLになるわけではありません。NULLの代入だけですべての解放後アクセスを防げるとは考えず、領域を利用する期間と、解放を担当する処理を明確にしましょう。

## まとめ

- 普通のローカル変数は、ブロックを抜けると寿命が終わる。
- mallocで確保した領域は、確保した関数から戻るだけでは解放されない。
- ポインタ変数自身の寿命と、指し先の寿命は別に考える。
- 寿命が終わるローカル変数のアドレスを返し、呼び出し元で使ってはいけない。
- 動的に確保した領域は、誰がfreeするかを決める。

## 理解度チェック

1. create_valueから戻ると、ptr自身と、mallocで確保した領域はそれぞれどうなりますか。
2. `return ptr;` は、ローカル変数ptr自身のアドレスを返す操作ですか。
3. `free(heap_ptr)` は、mainのローカル変数heap_ptr自身を解放しますか。
4. heap_ptrへNULLを代入すると、同じ領域を指していた他のポインタもNULLになりますか。

### 解答

1. ptr自身の寿命は終わりますが、mallocで確保した領域は解放されずに存在します。
2. いいえ。ptrに保存されたポインタ値を返します。ptr自身のアドレスは `&ptr` です。
3. いいえ。mallocで確保した指し先の領域を解放します。
4. いいえ。他のポインタ変数の値は変更されません。解放済みの領域へアクセスしないよう管理が必要です。
