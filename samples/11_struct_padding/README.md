# 今回使用する構造体

今回比較する構造体は、こちらです。

```c
struct Sample1 {
    char a;
    int b;
    char c;
};
```

もう一つはこちらです。

```c
struct Sample2 {
    int b;
    char a;
    char c;
};
```

よく見てください。この2つの構造体は、使っているメンバーは全く同じです。

違うのは、**メンバーの並び順だけ**です。

Sample1は、

```text
char → int → char
```

Sample2は、

```text
int → char → char
```

という順番になっています。

この並び順だけで、構造体のサイズやメモリ配置は変わるのでしょうか。

実際に確認してみましょう。

# サンプルプログラム

今回使用するファイルは、**struct_padding.c**です。

ソースコード全体はこちらです。

```c
#include <stdio.h>
#include "../mdump.h"

struct Sample1 {
    char a;
    int b;
    char c;
};

struct Sample2 {
    int b;
    char a;
    char c;
};

int main(void)
{
    struct Sample1 sample1 = {0};
    struct Sample2 sample2 = {0};

    sample1.a = 0x11;
    sample1.b = 0x22222222;
    sample1.c = 0x33;

    sample2.a = 0x11;
    sample2.b = 0x22222222;
    sample2.c = 0x33;

    printf("sizeof(Sample1) = %zu\n", sizeof(struct Sample1));
    mdump(&sample1, sizeof(sample1));

    printf("\n");

    printf("sizeof(Sample2) = %zu\n", sizeof(struct Sample2));
    mdump(&sample2, sizeof(sample2));

    return 0;
}
```

今回は、比較しやすいように、2つの構造体へ同じ値を設定しています。

```text
a = 0x11
b = 0x22222222
c = 0x33
```

こうすることで、メンバーの値ではなく、**メモリの並び方の違い**に注目できます。

また、`sizeof` で構造体全体のサイズを表示し、

その後、`mdump` を使って実際のメモリの状態も表示します。

今回は、**サイズだけではなく、実際のメモリを見ながら比較する**ことがポイントです。

# Sample2のメモリを見てみよう

続いて、`Sample2` のメモリを見てみましょう。

`Sample2` は、次のような構造体でした。

```c
struct Sample2 {
    int b;
    char a;
    char c;
};
```

メモリを図で表すと、このようになります。

```text
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 22 │ 22 │ 22 │ 22 │ 11 │ 33 │ 00 │ 00 │
├────┼────┼────┼────┼────┼────┼────┼────┤
│        b          │ a  │ c  │パディング │
└────┴────┴────┴────┴────┴────┴────┴────┘
        4バイト     1バイト 1バイト  2バイト
```

最初の、

```text
22 22 22 22
```

が、`b` の値です。

今回は、

```text
0x22222222
```

を設定しています。

`b` は `int` 型なので、4バイトの領域を使用します。

その次の、

```text
11
```

が、`a` の値です。

`a` は `char` 型なので、1バイトの領域を使用します。

続く、

```text
33
```

が、`c` の値です。

`c` も `char` 型なので、1バイトの領域を使用します。

`Sample2` では、最初に4バイトの `int` 型を配置し、その後ろに1バイトの `char` 型を2つ並べています。

そのため、メンバーとメンバーの間には、パディングがありません。

最後に2バイトのパディングが追加され、構造体全体のサイズは、8バイトになります。

# Sample1とSample2を比較しよう

2つの構造体を比較してみましょう。

`Sample1` の並び順は、

```text
char → int → char
```

でした。

メモリ上では、

```text
a → 3バイトのパディング → b → c → 3バイトのパディング
```

という並びになり、構造体全体のサイズは、12バイトでした。

一方、`Sample2` の並び順は、

```text
int → char → char
```

です。

メモリ上では、

```text
b → a → c → 2バイトのパディング
```

という並びになり、構造体全体のサイズは、8バイトでした。

同じ型のメンバーを持っていても、並び順を変えるだけで、構造体のサイズが変わっています。

```text
Sample1

メンバー     6バイト
パディング   6バイト
合計        12バイト


Sample2

メンバー     6バイト
パディング   2バイト
合計         8バイト
```

今回の例では、サイズの大きい `int` 型を先に配置することで、途中に入るパディングを減らすことができました。

一般的には、**サイズやアライメントの大きい型から並べる**ことで、パディングを減らせる場合があります。

# なぜ最後にもパディングが入る？

ここで、もう一つ疑問があります。

`Sample1` では、最後のメンバーである `c` の後ろに、3バイトのパディングがありました。

`Sample2` にも、最後に2バイトのパディングがあります。

なぜ、構造体の最後にも、パディングが必要なのでしょうか？

その理由を理解するために、構造体を配列にした場合を考えてみましょう。

例えば、`Sample1` の配列を作ります。

```c
struct Sample1 array[2];
```

配列の要素は、メモリ上へ連続して並びます。

`Sample1` のサイズは12バイトなので、2つの要素は次のように並びます。

```text
┌────────────── array[0]：12バイト ──────────────┐
│ a │ パディング │    b    │ c │ パディング │
└───────────────────────────────────────────────┘
┌────────────── array[1]：12バイト ──────────────┐
│ a │ パディング │    b    │ c │ パディング │
└───────────────────────────────────────────────┘
```

横に並べて見ると、このようになります。

```text
┌──────────── array[0] ────────────┐┌──────────── array[1] ────────────┐
│ a │  Pad  │    b    │ c │  Pad  ││ a │  Pad  │    b    │ c │  Pad  │
└──────────────────────────────────┘└──────────────────────────────────┘
              12バイト                           12バイト
```

それぞれの要素が12バイトなので、次の要素も正しい位置から始められます。

では、もし最後のパディングがなく、`Sample1` が9バイトだったらどうなるでしょう？

```text
最後のパディングがない場合

┌──────── array[0]：9バイト ────────┐┌──────── array[1] ────────
│ a │ Pad │    b    │ c │ a │ Pad │    b    │ c │
└────────────────────────────────────────────────
```

1つ目の構造体の直後から、2つ目の構造体が始まると、2つ目の構造体の先頭位置がずれてしまいます。

その結果、2つ目の構造体にある `int` 型の `b` を、適切な4バイト境界へ配置できなくなります。

そこで、構造体全体のサイズが、必要な境界の倍数になるように、最後にもパディングが追加されます。

今回の `Sample1` では、`int` 型に合わせて、構造体全体が4バイト単位になるように調整されています。

```text
9バイト
↓
最後に3バイト追加
↓
12バイト
```

`Sample2` でも同じです。

メンバーだけなら、

```text
b     4バイト
a     1バイト
c     1バイト
--------------
合計  6バイト
```

ですが、

構造体全体を4バイト単位にするため、最後に2バイトのパディングが追加されます。

```text
6バイト
↓
最後に2バイト追加
↓
8バイト
```

つまり、構造体の最後に入るパディングは、構造体を配列として連続して並べた場合でも、

それぞれの要素のメンバーを適切な位置へ配置できるようにする役割があります。

簡単に言えば、**最後のパディングは、次の構造体を正しい位置から始めるためでもある**ということです。

# 必ずメンバーを並べ替えればよいの？

ここまで見てきたように、

構造体では、サイズやアライメントの大きい型から並べることで、

パディングを減らせる場合があります。

今回の例では、

```text
Sample1
char → int → char
```

から、

```text
Sample2
int → char → char
```

へ並び順を変えることで、構造体のサイズを12バイトから8バイトへ減らすことができました。

では、構造体を書くときは、必ずサイズの大きい型から並べればよいのでしょうか？

必ずしも、そうとは限りません。

構造体のメンバーには、データの意味や役割があります。

関連するメンバーを近くに並べた方が、コードが読みやすくなることもあります。

また、ファイルへ保存するデータや、ネットワークで送受信するデータ、外部のライブラリやAPIと共有する構造体では、メモリ上の並び順が決められている場合があります。

そのような場合は、サイズを小さくするためだけに、自由にメンバーを並べ替えることはできません。

パディングを減らすことは、構造体を設計するときの選択肢の一つです。

特に、構造体を大量に配列として使う場合は、1つあたり数バイトの違いでも、全体では大きな差になることがあります。

例えば、1つの構造体で4バイト減らせた場合、100万個の要素では、約4メガバイトの違いになります。

ただし、サイズだけを優先するのではなく、読みやすさや互換性も考えながら、状況に応じて判断することが大切です。

# まとめ

今回は、**「パディングを減らす方法とは？」**というテーマで、2つの構造体のメモリ配置を比較しました。

`Sample1` は、

```text
char → int → char
```

という順番でした。

メモリ上では、メンバーの途中と最後にパディングが入り、構造体全体のサイズは、12バイトになりました。

一方、`Sample2` は、

```text
int → char → char
```

という順番でした。

サイズの大きい `int` 型を先に配置したことで、途中のパディングをなくすことができ、構造体全体のサイズは、8バイトになりました。

今回学んだポイントを整理します。

* メンバーの並び順によって、構造体のサイズが変わる
* `mdump` を使うと、パディングの位置と量を確認できる
* サイズやアライメントの大きい型から並べると、パディングを減らせる場合がある
* 構造体の最後にも、全体のサイズを調整するためのパディングが入る
* 最後のパディングは、構造体を配列として並べたときに、次の要素を適切な位置から始めるためでもある

前回は、構造体にパディングが追加されることを学びました。

今回は、そのパディングを、メンバーの並び順によって減らせることを確認しました。

`sizeof` の結果だけを見るのではなく、実際のメモリを確認することで、

なぜサイズが変わるのかを理解できます。

構造体を書くときは、メンバーの型だけでなく、並び順にも注目してみてください。
